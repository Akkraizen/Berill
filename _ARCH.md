# Архитектура Berill

## 1. Принципы

1. **Local-first.** Приложение всегда читает и пишет локальную базу (SQLite). Сеть нужна только для
   синхронизации, поэтому всё работает офлайн и мгновенно.
2. **Один универсальный формат данных.** Любая сущность (книга, операция, день привычек…) — это
   *запись*: коллекция + id + JSON-поля. Новые разделы не требуют миграций ни на клиенте, ни на
   сервере.
3. **Слияние без конфликтов.** Каждое поле записи хранит метку гибридных логических часов (HLC). При
   встрече двух версий для каждого поля побеждает более поздняя метка. Слияние коммутативно и
   идемпотентно — устройства гарантированно сходятся к одному состоянию.
4. **Один код на две платформы.** Kotlin Multiplatform + Compose Multiplatform: Android и Windows
   (JVM) делят 95 % кода.

## 2. Схема

```
┌────────────── Android ──────────────┐     ┌────────────── Windows ──────────────┐
│ плагины → core-api → ядро (core)    │     │ плагины → core-api → ядро (core)    │
│            → LocalStore (SQLDelight)│     │            → LocalStore (SQLDelight)│
│            → SyncEngine (Ktor)      │     │            → SyncEngine (Ktor)      │
└────────────────┬────────────────────┘     └────────────────┬────────────────────┘
                 │  POST /api/sync (HTTPS, Bearer-токен)     │
                 └──────────────┬────────────────────────────┘
                        ┌───────▼────────┐        ┌─────────────────────┐
                        │ Ktor server    │◄───────│ разовый перенос     │
                        │ merge + rev    │        └─────────────────────┘
                        └───────┬────────┘
                        ┌───────▼────────┐
                        │ PostgreSQL     │
                        └────────────────┘
```

## 3. Модель записи

```kotlin
SyncRecord(
    collection = "habit_days",
    id = "2026-10-19",
    fields = {"chess_games": 30, "deutsch": 20},
    clocks = {"chess_games": "001760900000000-00000-a1b2c3d4", "deutsch": "…"},
    deletedAt = null,
    rev = 42,
)
```

* **HLC-метка** `ммммммммммммммм-сссss-устройство` сравнивается как строка. Часы не идут назад, даже
  если системное время устройства сбилось, и `догоняют` метки других устройств.
* **Слияние по полям**: отметки разных привычек в один день с телефона и ПК не затирают друг друга.
* **Удаление** — `deletedAt`. Запись скрыта, если надгробие новее всех полей; если поле потом
  изменят снова, запись `воскреснет` (так безопаснее, чем потерять данные).

## 4. Протокол синхронизации

Один запрос:

```
POST /api/sync            Authorization: Bearer <токен>
{ "deviceId": "a1b2c3d4", "since": 40, "changes": [SyncRecord, …] }

← { "records": [SyncRecord, …], "cursor": 57, "hasMore": false }
```

Сервер в одной транзакции:

1. блокирует счётчик ревизий пользователя (`SELECT … FOR UPDATE`);
2. сливает каждое присланное изменение с серверной версией; если содержимое изменилось — выдаёт
   записи новый `rev`;
3. возвращает все записи с `rev > since` (пачками по 2000, `hasMore` — есть ещё).

Клиент:

1. берёт записи с `dirty = 1` и запоминает их локальную `version`;
2. отправляет, применяет ответ слиянием, сохраняет `cursor`;
3. снимает `dirty` только с тех записей, которые не менялись во время запроса (`version` совпадает).

Когда запускается: через 2 секунды после локального изменения, раз в минуту и по кнопке.

## 6. Импорт из Obsidian

Разовый скрипт `tools/obsidian-import` (не входит в сборку и не часть приложения) проходит по папкам
хранилища, читает YAML-свойства и текст заметок и отправляет записи на сервер. Метки полей берутся
из **даты изменения файла**, поэтому:

* повторный импорт тех же заметок ничего не перезапишет;
* правки, сделанные позже в приложении, всегда новее импорта.

Не переносятся (пока): изображения (обложки остаются ссылками на файлы), код панелей Datacore.

## 7. Безопасность

* Только HTTPS снаружи; токены — минимум 16 символов, хранятся в переменной `HUB_TOKENS`.
* Данные разделены по пользователю (`user_id`) на уровне каждой таблицы.
* Следующий шаг: вход по паролю с выдачей токена на устройство и отзыв токенов.

## 9. Почему так, а не иначе

* **Не CRDT-библиотека (Automerge/Yjs).** Для записей с плоскими полями LWW по полям даёт то же
  поведение при гораздо меньшей сложности. Если понадобится совместное редактирование длинных
  текстов (тело заметки), именно поле `body` можно будет перевести на текстовый CRDT.
* **Не Firebase/Supabase.** Свой сервер на том же Kotlin, полный контроль над данными, без
  зависимостей от внешних сервисов.
* **Не синхронизация файлов.** Файловая синхронизация даёт конфликты на уровне целых файлов; записи
  с полевыми метками сливаются автоматически.
* **Связь с cenno.** Ваш репозиторий `cenno` (`Backend for Akraizen Hub`) — хорошее место для
  серверной части, если захочется переписать её на Rust: протокол из раздела 4 не привязан к Kotlin.

## 10. Решение: Kotlin Multiplatform (а не Flutter или Tauri)

Рассматривали три варианта клиента (октябрь 2026):

|                       | Compose Multiplatform                                                               | Flutter                                                           | Tauri 2 + Vue                     |
|-----------------------|-------------------------------------------------------------------------------------|-------------------------------------------------------------------|-----------------------------------|
| Material 3 Expressive | официальные компоненты Google (material3 1.10 alpha, на базе Jetpack Material3 1.5) | в основном фреймворке не разрабатывается; только сторонние пакеты | нет, всё вручную в CSS            |
| Windows               | JVM: установщик ~45–50 МБ, старт ~1,3 с → ~0,65 с с AOT (CMP 1.12)                  | нативно, легче и быстрее                                          | самое лёгкое (WebView2)           |
| Android               | нативный Compose                                                                    | нативный рендер Flutter                                           | веб-интерфейс в WebView           |
| Язык / общий код      | Kotlin везде, протокол общий с сервером                                             | Dart, протокол пришлось бы дублировать                            | Rust + TS, сервер можно в `cenno` |

**Выбор — Compose Multiplatform**: официальный Expressive, нативный Android и один язык с сервером
важнее, чем вес Windows-версии. Вес компенсируем так:

* release-сборка через ProGuard (`./gradlew :composeApp:packageReleaseMsi`);
* урезанный набор модулей JDK в упакованном рантайме (`nativeDistributions.modules`);
* AppCDS/AOT-кэш, когда Compose Multiplatform 1.12 станет стабильным (блок `aot` в
  `composeApp/build.gradle.kts`).

## 11. Структура проекта Berill

Проект создан мастером Kotlin Multiplatform (Android + Desktop + Server). Все пакеты —
`dev.akkraizen.berill.*`.

```
protocol/            протокол синхронизации (SyncRecord, HLC, слияние) — общий с сервером
core-api/            контракты для плагинов (пакет …berill.api)
core/                ядро (…berill.core): data/ sync/ plugin/ nav/ notes/ ui/ + фабрики Android/Desktop
plugins/habits/      плагин `Привычки` (…berill.plugins.habits)
app/shared/          список плагинов сборки (Plugins.kt)
app/androidApp/      точка входа Android → createAndroidCore(context, BerillPlugins) + BerillShell
app/desktopApp/      точка входа Windows → createDesktopCore(BerillPlugins) + BerillShell
server/              сервер синхронизации
tools/obsidian-import/  разовый перенос из Obsidian (вне сборки)
```

Граф зависимостей: `plugins/* → core-api`; `core → core-api, protocol`;
`app:shared → core, plugins/*`;
`server → protocol`. Плагин не видит ни базу, ни сеть, ни другие плагины.

## 12. Ядро и плагины

**Ядро** (`core`) — это всё, без чего приложение не имеет смысла, и ничего сверх:
локальная база и синхронизация, реестр плагинов, оболочка (тема, боковая панель со всеми разделами,
`Главная`,
`Настройки`) и простые **заметки** (заголовок + текст, поиск, автосохранение).

**Плагин** реализует `BerillPlugin` из `core-api`:

| Член                                   | Зачем                                                                                              |
|----------------------------------------|----------------------------------------------------------------------------------------------------|
| `id`, `title`, `icon`, `order`         | стабильный идентификатор, название, иконка Material Icons (`ImageVector`) и место в боковой панели |
| `collections`                          | коллекции, которыми владеет плагин (экран `Данные`, экспорт)                                       |
| `@Composable Screen(ctx)`              | экран раздела; внутренние экраны — строковые маршруты `ctx.nav.route`                              |
| `homeCards(ctx)` / `quickActions(ctx)` | карточки и быстрые действия на главной                                                             |
| `provides(ctx)`                        | возможности для других плагинов (`Capability`, например `DeadlineSource`)                          |

`PluginContext` даёт плагину: `data` (типизированные и `сырые` коллекции поверх LocalStore — все
записи автоматически синхронизируются), `nav`, `capabilities`, `settings`
(синхронизируемые настройки плагина) и `scope`.

Правила:

* плагины подключаются при сборке (Gradle-модули), а не загружаются во время работы — так работает
  R8/ProGuard, Android и будущий iOS;
* включён/выключен — синхронизируемая запись `settings/plugins` (поле на плагин); выключение
  скрывает раздел, но данные остаются и синхронизируются;
* `id` и имена коллекций не меняются никогда; id
  `core, notes, home, settings, sections, sync, plugins`
  зарезервированы ядром;
* плагины не зависят друг от друга: общение — только через интерфейсы `Capability` в `core-api`.

Добавить раздел: модуль `plugins/<имя>` (копия `build.gradle.kts` из `plugins/habits`) →
`include` в `settings.gradle.kts` → зависимость в `app/shared/build.gradle.kts` → строка в
`Plugins.kt`.

* Эмодзи в интерфейсе заменены на Material Icons

### Внешние API (v0.7)

Плагины ходят в сеть только через `PluginContext.http` (`HttpAccess.getJson`) — HTTP-клиент (Ktor)
есть только у ядра; плагин получает JSON и разбирает его хелперами `str/int/arr/obj` из `core-api`.
Общая панель поиска — `OnlineSearchPanel` (UI-кит).

| Раздел                    | API                                                                                                                       | Ключ                                        | Где задать             |
|---------------------------|---------------------------------------------------------------------------------------------------------------------------|---------------------------------------------|------------------------|
| Чтение                    | Google Books API v1 (`/volumes?q=`, `/volumes/{id}`)                                                                      | необязателен (без него чаще 429)            | Чтение → шестерёнка    |
| Просмотры, аниме          | Shikimori (`/api/animes`, `/api/animes/{id}`), запасные домены shiki.one, shikimori.me                                    | не нужен (нужен User-Agent — ставит ядро)   | —                      |
| Просмотры, фильмы/сериалы | Kinopoisk API Unofficial (`/api/v2.1/films/search-by-keyword`, `/api/v2.2/films/{id}`, `/seasons`), заголовок `X-API-KEY` | обязателен, бесплатный (500 запросов/сутки) | Просмотры → шестерёнка |

Ключи лежат в синхронизируемых настройках плагина (`settings/plugin.<id>`), в коде их нет. При
добавлении из поиска проверяется дубликат по названию; статус и даты ставятся как при переносе на
доске.

### Настройки (v0.8)

* **Оформление** (синхронизируемая запись `settings/appearance`): тема
  `Как в системе / Светлая / Тёмная`
  и акцентный цвет — 11 готовых (зелёный по умолчанию — вручную выверенная палитра), `Обои`
  (Material You, Android 12+) или свой `#RRGGBB`. Палитра Material 3 от акцента строится библиотекой
  MaterialKolor.
* **Разделы и каталог.** Состояние плагина: установлен (`settings/plugins_installed`) и включён
  (`settings/plugins`). Плагин с `installedByDefault = false` (все новые) появляется в
  `Каталоге разделов` — `Установить`
  добавляет его в панель; `Удалить` возвращает в каталог; выключенный остаётся установленным, но
  скрыт. Данные раздела при этом не трогаются.
* **Настройки раздела.** Плагин объявляет `hasSettings = true` и `@Composable Settings(ctx)`; ядро
  показывает их страницей `Настройки · <раздел>` (`Destination.PluginSettings`), из раздела —
  `ctx.nav.openSettings()`. Сейчас: Привычки — цели идеальных дней; Планировщик — показ дедлайнов;
  Чтение — ключ Google Books; Просмотры — ключ Кинопоиска; Финансы — свои категории
  расходов/доходов; Учёба — типы заданий.

### Анимации (v0.8.1)

* Движение — пружины Material 3 Expressive (`BerillMotion` в `core-api`: spatial — с лёгким
  `перелётом`
  для движения и размеров, effects — без него для прозрачности и цвета).
* Боковая панель на широком экране — одна панель с анимированной шириной (280 ↔ 88 dp): подписи
  растворяются и сворачиваются, иконка-переключатель поворачивается, выделение пункта
  перекрашивается плавно. На телефоне — выдвижная панель Material 3.
* Экраны — схема Material `shared axis`: смена разделов — вертикальная ось (новый экран поднимается
  снизу с увеличением 0.96→1, старый уходит вверх), переход вглубь/назад — горизонтальная ось (сдвиг
  на 1/5 ширины). Старый экран гаснет за 120 мс, новый проявляется за 300 мс с задержкой 90 мс;
  сдвиг — пружина 0.85/300. Внутри раздела —
  `AnimatedRoute(route) { r -> … }` (замена `key(route)`); у уходящего экрана маршрут `заморожен`
  (`RouteScopedContext`).
* Элементы: плитки статистики (число `прокручивается`), прогресс, высота карточек, канбан (карточки
  появляются в новой колонке), элементы списков (`animateItem`), результаты поиска, галочки
  планировщика, кроссфейд обложек, плавная смена темы и акцентного цвета (`animateColorScheme`).

### Параметры синхронизации (v0.8.2)

* `SyncOptions` (core/sync) хранится в локальной meta `sync_options` — у каждого устройства свои
  параметры.
* Автосинхронизация вкл/выкл и период (1 / 5 / 15 / 60 мин); выключена — только кнопкой
  `Синхронизировать`.
* Что синхронизировать: тема и акцент (`settings/appearance`), набор разделов (`settings/plugins`,
  `plugins_installed`), настройки разделов (`settings/plugin.<id>`), данные — по разделам
  (коллекции).
* Исключённые записи не отправляются и не принимаются; локальные изменения остаются `грязными` и
  уйдут после повторного включения. Повторное включение сбрасывает курсор — следующая синхронизация
  забирает пропущенное с сервера целиком (слияние LWW по HLC).

### Реестр коллекций (v0.8.3)

* `protocol.Collections` содержит только коллекции ядра: `notes` и `settings`. Сервер хранит любые
  коллекции, имена ему не нужны.
* Имена коллекций плагина объявляет сам плагин в `BerillPlugin.collections` (константы в объекте
  плагина, например `BooksPlugin.BOOKS`).
* `CollectionRegistry` (core/plugin, `core.collections`) собирает их при запуске и проверяет: формат
  `[a-z][a-z0-9_]{0,39}`, нет совпадений с ядром и между плагинами. Ошибка — исключение на старте.

* Инструмент импорта (tools/obsidian-import) держит свою копию имён в `importer/Collections.kt`.

### Markdown (v0.9)

* `core-api/api/ui/markdown`: собственный разбор и отрисовка без сторонних библиотек (одинаково на
  Android и ПК).

### Интернационализация (v1.0)

* Общие переводы находятся в `core-api/src/commonMain/localization/<locale>.json`.
  Переводы встроенных плагинов — в `plugins/<plugin>/src/commonMain/localization/<locale>.json`.
  У файла есть `locale`, `nativeName`, `pluralRule` и объект `messages` с ключами.
  Пример сообщения: `"habits.doneOf": "Выполнено {done} из {total}"`.
  В Kotlin хранятся только ключи и аргументы:

  ```kotlin
  val title = pluginI18n.tr("habits.title")
  fun doneOf(done: Int, total: Int) = pluginI18n.tr("habits.doneOf", "done" to done, "total" to total)
  val text = pluginI18n.text("habits.doneOf", "done" to 2, "total" to 3)
  ```

* `Tr` откладывает поиск до вызова `()` и работает вне Compose. `I18n.text` сразу возвращает
  строку по ключу; `I18n.plural(key, count)` выбирает форму и подставляет `{n}`.
  Формы хранятся объектом `{"one": "{n} задача", "few": "{n} задачи", "other": "{n} задач"}`.
  Доступны zero/one/two/few/many/other; `other` обязательна. `I18n.list` читает массивы строк
  (месяцы и дни недели также вынесены в JSON).
* Коды локалей регистронезависимы, `_` нормализуется в `-`. Поиск сообщения:
  точная локаль → родительские теги → запасная локаль (`en`) → первый имеющийся перевод.
  Для отсутствующего ключа возвращается сам ключ; пропущенный обязательный аргумент — ошибка.
  Литералы фигурных скобок записываются как `{{` и `}}`; аргументы повторно не интерполируются.
* Обычная задача Gradle `generateLocalization` из корневого `build.gradle.kts` (без отдельного плагина локализации) генерирует упакованные каталоги в `build/generated/localization`
  из JSON-файлов. Это обеспечивает один синхронный API в Android/JVM без чтения файлов
  внутри Compose и без доступа внешнего плагина к файловой системе. Генерируемый Kotlin
  вручную не редактируется. Новая локаль добавляется файлом; её имя и правило берутся из метаданных,
  и локали общего каталога автоматически появляются в настройках и onboarding после сборки.
  Неполные каталоги плагинов используют свой fallback для недостающих переводов.
* Общий движок `TranslationCatalog` находится в `plugin-sdk/sdk/i18n`; `core-api/api/i18n`
  добавляет активный язык и состояние Compose. Правила other/one-other/zero-one-other/russian
  встроены, пользовательские правила можно зарегистрировать через `PluralRules.register`.
  При fallback правило выбирается для языка найденного сообщения.
* `berill.plugin` автоматически подключает генерацию локализаций модуля. Каждый встроенный
  плагин создаёт свой `pluginI18n = Localization(<Plugin>CatalogData.files)` и обращается через
  `pluginI18n.tr/text/plural/list`. Объект `Localization` использует активный `I18n.language`,
  а ключи и fallback ищет только в своём каталоге. Ключи разных модулей могут совпадать;
  глобальная регистрация или объединение переводов не нужны.
* У каждого модуля остаётся свой каталог ключей: `UiText`, `CoreText`, `BooksText`, `WatchingText`,
  `HabitsText` и другие. Добавление перевода или изменение текста не требует изменения этих классов.
* Внешний плагин хранит JSON в своём `src/commonMain/localization`, получает сгенерированные
  данные и задаёт `override val translations = TranslationCatalog.fromJson(CountersCatalogData.files)`.
  `tr("counters.someKey", "value" to value)` ищет строку на языке хоста. Имена и описания
  в `berill-plugin.json` тоже остаются файловыми переводами; для страниц и карточек из
  метаданных строится отдельный каталог с ключами.
* Настройка языка хранится в `settings/appearance`, синхронизируется вместе с темой и принимает
  все локали из каталога. Ядро обновляет `I18n.language`; `key(I18n.language)` пересобирает оболочку.
* Хранимые значения (статусы, виды операций, разделы словаря, категории по умолчанию, шаблоны,
  которые потом разбираются) не переводятся — для экрана есть функции-подписи (`statusLabel`,
  `kindLabel`, `sectionLabel`…).

## Безопасность

### Встроенные плагины (plugins/*) — изоляция на этапе сборки

- Конвенция `berill.plugin` проверяет каждый модуль (`verifyPluginSources`, запускается перед
  компиляцией):
  только `commonMain`/`commonTest`, зависимости — только `:core-api`, без платформенных API
  (`java.*`, `android.*`, `kotlin.io` файлы, потоки, рефлексия), без `io.ktor`/`coil3`,
  внутренностей приложения (`core`, `protocol`, `sdk`), `LocalUriHandler` и буфера обмена.
- Coil в `core-api` — `implementation`: картинки по ссылке только через `Cover` / Markdown.
- Права: `BerillPlugin.permissions = PluginPermissions(network = listOf(хосты), anyImageHost)`.
  `ctx.http` (GuardedHttpAccess) пускает только HTTPS к объявленным хостам, иначе
  `NetworkNotAllowedException`. Картинки: `LocalImagePolicy` (ядро подставляет права раздела вокруг
  его страниц, карточек и настроек); локальные файлы и прочие схемы не грузятся никогда.
- Ссылки: `isSafeExternalLink` / `rememberOpenLink()` — наружу только http (s) и mailto; в Markdown
  ссылки других схем показываются текстом.
- Секреты: `ctx.secrets` (SecretStore) — ключи API только на устройстве (Windows — DPAPI, Android —
  Keystore), не синхронизируются. `migrateSecretFromSettings` переносит старые ключи из настроек.
  Токен сервера синхронизации тоже в хранилище секретов.

### Сквозное шифрование синхронизации (SyncEncryption)

- Ключ AES-256 из пароля: PBKDF2-HMAC-SHA256, 310 000 итераций; соль и проверочное значение —
  открытая запись
  `settings/e2e`. Ключ хранится только в хранилище секретов устройства.
- Шифруются значения полей (`e1:` + base64 (nonce + AES-GCM), AAD = коллекция/id/поле); имена полей,
  id и HLC-метки остаются открытыми — по ним сервер сливает версии.
- Синхронизация сначала забирает изменения (чтобы узнать о включённом шифровании), потом отправляет
  свои. Без ключа (Locked) устройство ничего не отправляет и не применяет зашифрованное; после ввода
  пароля курсор сбрасывается.
- Включение: `restampAll()` даёт всем полям новые метки — открытые значения на сервере
  перезаписываются шифротекстом.

### Сторонние плагины — отдельный процесс (`:plugin-sdk`, `core/external`)

- Автор пишет KMP-модуль (`id("berill.external-plugin")`) против `:plugin-sdk`: класс
  `ExternalPlugin`, интерфейс — DSL `UiBuilder` (дерево `UiNode`, рисует ядро), возможности — `Host`
  (данные своих коллекций, свои настройки, HTTPS к хостам из манифеста, навигация, toast). Compose в
  SDK нет.
- Пакет `.tplugin` (zip): `berill-plugin.json` (манифест: id, страницы, карточки, коллекции
  `<id>_*`, права),
  `plugin.jar`, `classes.dex` (d8). Сборка: `./gradlew :<модуль>:packageBerillPlugin`. Пример —
  `external-plugins/counters`.
- Установка: Настройки → `Сторонние плагины` → файл → экран с правами → пакет кладётся в папку
  плагинов; подключается после перезапуска (обновление и удаление тоже). Ошибки манифеста и
  конфликты id/коллекций — плагин не подключается, приложение работает.
- Протокол: JSON-строки (`sdk.protocol`): Load/Code/Render/Event/Reply ↔
  Loaded/Tree/Call/Invalidate/Log. Каждый вызов плагина ядро выполняет через его PluginContext
  (ScopedDataAccess, GuardedHttpAccess) — права проверяет ядро. Таймауты: загрузка 20 с, ответ 8 с
  (иначе процесс останавливается); 3 сбоя за минуту — плагин выключается до `Перезапустить`.
- Windows: дочерняя JVM (`-Xmx160m`, classpath через @argfile; в установленной сборке — сам exe с
  флагом
  `--berill-plugin-runner`). Защита: BytecodeVerifier (таблица констант: только разрешённые классы,
  без рефлексии Class.*, без вызовов MethodHandle) + FilteringClassLoader (`PluginClassRules`:
  запрещённый класс = `класса нет`). stdout плагина — в журнал, stdin пуст.
- Android: сервис `PluginRunnerService` с `android:isolatedProcess="true"` (свой uid без разрешений:
  нет файлов приложения, сети, данных других приложений), на Android 10+ — процесс на каждый плагин
  (bindIsolatedService). dex приходит по Binder кусками, грузится InMemoryDexClassLoader через тот
  же фильтр классов.
- Проверено: пример `counters` проходит проверку байткода и работает через протокол; класс с
  java.io.File, System.exit, Thread, Class.forName, MethodHandles, java.net, sdk.protocol
  отклоняется проверкой, а без неё — загрузчиком (NoClassDefFoundError).

## Тренировки: картинки упражнений

- Источник — Free Exercise DB (github.com/yuhonas/free-exercise-db): ~800 упражнений, по два кадра
  (начало/конец движения), общественное достояние (Unlicense), без ключа. JSON `dist/exercises.json`
  грузится один раз за запуск (`ExerciseDb`), фото —
  `raw.githubusercontent.com/.../exercises/<id>/0.jpg|1.jpg`. В правах раздела — хост
  `raw.githubusercontent.com`.
- Подбор (`imageFor`): выбор пользователя (настройка `exerciseImages`: id каталога → id в базе, "" —
  без картинки) → подсказки для встроенных (`HINTS`, несколько вариантов названий/id) → точное
  английское название → похожее название (доля общих слов ≥ 0,5, бонус за совпадение снаряда).
- Каталог: миниатюры в списке и в выборе упражнения; карточка упражнения — `гифка` (кадры сменяются
  через 1,1 с, кроссфейд, пауза), `Другая картинка` (поиск по базе), `Подобрать автоматически`,
  `Без картинки`, пошаговая инструкция (англ.).

## Сервер: токены синхронизации

- Таблица `tokens` (id, пользователь, устройство, SHA-256 токена, создан/использован/отозван). Сам
  токен (`tsr_` + 32 случайных байта base64url) показывается один раз при создании.
- CLI в том же jar: `token create <пользователь> [--name <устройство>]`,
  `token list [<пользователь>]`, `token revoke <id>`. Docker:
  `docker compose run --rm server token create akkraizen --name phone`; Gradle:
  `./gradlew :server:run --args="token create akkraizen"`.
- Проверка bearer-токена: сначала `HUB_TOKENS` (старый способ, по желанию), затем база (хэш, не
  отозван); время последнего использования пишется не чаще раза в 10 минут.
